# Session Notes — 2026-08-18/19

Started from the App Store Connect crash graph for 1.6.0 (20 opt-in
crashes, two spikes: ~10 on Jul 7-8, ~5 on Aug 15-16) plus the report
that Android misbehaved on Hebrew-locale phones. Both had a concrete
cause. Everything below is in `v1.6.1-crash-and-rtl-fixes`.

## Done

### The crash: `popToTop` is not on the navigation container ref
**Symptom:** a free user opens Adventure, picks a world, taps a
premium-locked level → app terminates.

`GameShell.handleAdventureLevelPress` called
`navigationRef.current?.popToTop()`. `popToTop` is a **StackAction**,
and `createNavigationContainerRef` only proxies `CommonActions`
(navigate / goBack / reset / setParams / preload / replaceParams /
navigateDeprecated) plus a fixed helper list — verified in
`node_modules/@react-navigation/core/src/createNavigationContainerRef.tsx`
and `BaseNavigationContainer.tsx:230`. So `current` is non-null (the
`?.` never short-circuits), `.popToTop` is `undefined`, and the call
throws a TypeError. In a release build with no error boundary that is
`RCTFatal` → hard crash.

**Fix:** `navigationRef.current?.dispatch(StackActions.popToTop())`.
`dispatch` *is* on the ref.

This matches the crash pattern exactly: low absolute count, clustered
spikes (a child tapping a locked level repeatedly), 1.6.0 only —
Adventure + premium gating are new in 1.6.

### RTL on Hebrew/Arabic devices
`android/app/src/main/AndroidManifest.xml` had `android:supportsRtl="true"`
(the RN template default) and nothing in the codebase ever touched
`I18nManager`. On an RTL-locale device the whole UI mirrored: the
ten-frame grid reversed, and subtraction rendered as `? = 2 - 5`. For a
maths app that is not cosmetic — it teaches the wrong thing.

`I18nUtil.isRTL()` (ReactAndroid `.../modules/i18nmanager/I18nUtil.kt`)
starts with `applicationHasRtlSupport(context)`, which reads
`ApplicationInfo.FLAG_SUPPORTS_RTL` straight from the manifest. So the
manifest flag is the authoritative kill switch: it applies on the very
first launch, with no restart and no SharedPreferences race.

- `AndroidManifest.xml`: `android:supportsRtl="false"`
- `index.js`: `I18nManager.allowRTL(false)` / `forceRTL(false)` /
  `swapLeftAndRightInRTL(false)` — belt and braces, and covers iOS if
  an RTL localization is ever shipped.

iOS is almost certainly unaffected: `RCTI18nUtil.isRTL` gates on
`isApplicationPreferredLanguageRTL`, which follows the app's bundled
localizations, and the app ships none.

### The app font was never actually applied
`installFredoka.ts` monkey-patched `Text.render`. RN 0.84's
`Libraries/Text/Text.js` ends in `export default TextImpl` — a plain
function component, no `forwardRef`, therefore no `render` property.
The assignment was inert and the app had been rendering in Roboto /
San Francisco since the font was added. `TextInput.defaultProps` was
equally dead under React 19.

- Deleted `installFredoka.ts`; added `src/components/common/AppText.tsx`
  and codemodded 36 files to import `Text` from it.
- `Emoji.tsx` and `ErrorBoundary.tsx` deliberately keep the raw RN
  `Text` — the first sets its own emoji face, the second must not gain
  dependencies.
- `Animated.Text` bypasses the wrapper (reanimated wraps the raw RN
  `Text`), so `ModeChoice.styles.title` and `LevelCompleteScreen`'s
  title/message/newBest name `fontFamily: FREDOKA_FAMILY` directly.

**Font naming — measured, not guessed.** `assets/fonts/Fredoka.ttf` is
a *variable* font. Registering it through CoreText shows family
`Fredoka` with five real members (Light −0.23, Regular 0.0, Medium 0.2,
SemiBold 0.3, Bold 0.4). The old per-weight names
(`Fredoka-Regular`/`-Medium`/`-SemiBold`/`-Bold`) match nothing.
`Fredoka-Light` is the *PostScript* name, not a family name, and passing
it makes RN take its single-member fallback branch and collapse every
weight. So `FREDOKA_FAMILY = 'Fredoka'` on **both** platforms.

**Expect a visible change:** the app now renders in Fredoka for the
first time.

### Other fixes
- `ErrorBoundary` + `installErrorHandler`: an unhandled JS error shows a
  recovery screen instead of terminating. Promise rejections are hooked
  through `HermesInternal.enablePromiseRejectionTracker` (RN's
  `polyfillPromise.js` takes the Hermes branch, so the `promise` npm
  polyfill this originally patched is never constructed) and are
  recorded **diagnostic-only** — a rejection does not kill the process
  and must not put a full-screen error in front of a 5-year-old.
- `useVoice`: the cache kept every one of 1275 clips per language alive
  forever (3810 mp3s bundled), each a live AVAudioPlayer/MediaPlayer
  holding its file open. Now a 48-entry LRU, fully released on
  background. The queue's `busy` flag got an ownership token: a
  `stop()` could previously strand it (voice silent for the rest of the
  screen) or steal it from a newer job (clip truncated, `onDone`
  dropped — which in Adventure is how an answer gets recorded).
- `useIAP`: a rejected `finishTransaction` swallowed both
  `setPurchasing(false)` and the premium grant — the parent paid and got
  nothing, with a wedged spinner. Now try/catch/finally, with the grant
  gated on the purchase not being Android `PENDING` (cash / carrier
  billing / approval) so a still-unpaid purchase cannot unlock premium.
- `GameShell`: onboarding used `name` as its "already set up" flag, but
  the name field was removed in 4a6c53f, so the flag was permanently
  false. Theme, language and `lastMode` never restored and the setup
  sheet reopened on every Free Play entry. Explicit `onboarded` flag on
  `PlayerData` with a `data.onboarded ?? data.name !== ''` migration.
  Language is restored **only** when onboarded — `defaultPlayerData`
  hard-codes `'ro'`, and applying it on a fresh install would override
  the device-locale detection.
- `AdventureLevelScreen`: level progression no longer depends on a voice
  callback surviving (once-only latch + 8s watchdog), and the
  next-problem instruction timer is cancelled on the **correct** path
  only — cancelling it on a wrong answer silenced the problem for good.
- `ParentalGate`: an Arabic/Persian/Hindi IME sends its own digit
  glyphs, which the `[^0-9]` filter silently dropped, so the parent
  typed and nothing appeared. Now normalised to ASCII first.
- `useSound`: a clip finishing load after unmount is released instead of
  leaked; `setCategory` aligned with `useVoice` (both `('Playback', true)`,
  so a parent's music keeps playing).
- `VoiceEntry` gained the `de` field all 1275 entries already carried —
  that alone was hiding 1275 tsc errors.

## Android — nothing verified, here is what to do

**No Android code is outstanding.** Everything needed is committed. But
nothing on this branch was built or run on Android — there is no JDK or
Android SDK on the Mac, so all verification above is iOS-only.

1. **Version bump — your call, deliberately untouched.**
   `android/app/build.gradle` is still `versionName "1.4.0"` /
   `versionCode 9`, while iOS is now `1.6.1 (7)`. Android never shipped
   1.5 or 1.6, so I did not guess what your Play track expects.

2. **Verify the RTL fix — this is the one that matters most here.**
   Set the device or emulator language to Hebrew (or Arabic), launch,
   and confirm nothing mirrors: the ten-frame grid must fill
   left-to-right and subtraction must read `5 - 2 = ?`. This is the fix
   for the original report and the only platform where it is load-bearing.

3. **Verify the font, especially bold.** `fontFamily: 'Fredoka'`
   resolves by *filename* on Android: `ReactFontManager.createAssetTypeface`
   builds `fonts/` + family + one of `["", "_bold", "_italic",
   "_bold_italic"]` + `.ttf`. `assets/fonts/Fredoka_bold.ttf` is
   committed (a static wght=700 instance of the variable font, generated
   with fontTools) and already copied to
   `android/app/src/main/assets/fonts/`. Without it, `Typeface.create`
   falls through to the **system** font and every `fontWeight >= 700`
   renders in Roboto next to Fredoka body text. Check a screen with
   mixed weights — the mode-choice screen shows '900', '800', '700' and
   '600' side by side.

4. **Do not run `npx react-native-asset` unless you need to.** Both font
   files are already in place for Android. Running it is harmless for
   Android but will also add `Fredoka_bold.ttf` to iOS `UIAppFonts`,
   which iOS does not need — it already has Bold from the variable font,
   and the extra registration just duplicates the family member.

5. Build prerequisites are unchanged and already in `CLAUDE.md`
   (Gradle 8.13, JDK 17+, AsyncStorage's local Maven repo).
