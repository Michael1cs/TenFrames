### Voice queue: clear between problems
After fixing module-level voice serialization in the previous session,
two new symptoms showed up where the queue still chained the PREVIOUS
problem's instruction onto the new problem's voices.

**Symptom 1 (Adventure, Farm Share):** "după prima provocare la sfârșit
repetă ce spune la începutul provocării". When the child solved problem
0 quickly, the `share_intro` clip was still mid-play. Then problem 1's
voices queued behind it, so the kid heard the end of problem 0's intro
before the new problem started.

**Fix:** call `voice.stop()` inside the scheduled voice action in
`AdventureLevelScreen` right before the new action fires — clears any
leftover audio from the previous problem in the same screen.

**Symptom 2 (Free Play, addition/subtraction):** "apare vocea anterioară
cu provocarea înainte de a începe provocarea nouă". Same root cause —
`pre_have_<theme>_<n1>` from problem 0 could still be queued or playing
when problem 1's voices got enqueued.

**Fix:** in `GameShell`'s per-problem `useEffect`, call `voice.stop()`
before the new `queueVoice(pre_have…)` / `queueVoice(instr_…)` calls.
Skipped on the very first problem of a session so the welcome isn't
clipped. Praise from the previous correct answer (post_great_*) might
get cut if it's still queued at the moment the new problem voice fires
— acceptable tradeoff vs hearing the wrong instruction.

### Voice stops on navigation
The kid taps Adventure before "Welcome to Ten Frames…" finishes — the
welcome (and the queued mode_question + mode_adventure + mode_freeplay)
were still playing seconds later over the new screen.

Multi-layer fix:

- `useVoice.ts` exports a `playGen` counter. Every `clearVoiceQueue()`
  / `setVoiceEnabled(false)` bumps it. The drain loop captures the
  current gen when it starts loading a clip; when the load Promise
  resolves it bails if the gen has moved on. Same check before
  `sound.play()` and inside the playback completion callback. Stops
  the "load already in flight when stop() was called" leak — the
  sound used to play anyway when the load finished.
- New `clearPendingVoiceQueue()` — soft variant that drops pending
  items but lets the in-flight clip finish (used between Free Play
  problems so legitimate praise isn't cut mid-sentence).
- `GameShell.tsx`:
  - `Stack.Navigator screenListeners.blur` calls `shell.voice.stop()`
    on every route change. Covers Home ↔ FreePlay ↔ AdventureWorlds
    ↔ AdventureLevels ↔ AdventureLevel.
  - Every modal-open press handler (ℹ️ Info, 👑 Premium, 🎨 Theme,
    🎨 Stickers, 🏆 Dashboard, ⚙️ Settings) calls `ctx.voice.stop()`
    first. Modals don't trigger stack blur so they need explicit
    stop.
- `ModeChoice.tsx` switched its narration sequence from `useEffect`
  to `useFocusEffect`. Critical because react-navigation native-stack
  keeps blurred screens MOUNTED — a plain `useEffect` cleanup only
  fires on unmount, so the welcome sequence's pending `setTimeout`s
  would keep calling `voice.play()` long after the kid navigated
  away. `useFocusEffect`'s cleanup fires on every blur.
- `PlayerSetup.tsx` cleanup now also calls `voiceRef.current.stop()`
  when the modal is dismissed (kid picks a theme and taps Play).

### Pause between Free Play problems
"Voice barely finishes, next challenge starts."

Two adjustments:

- `GameShell.tsx` uses `clearPendingVoiceQueue()` (soft) instead of
  `voice.stop()` when queueing the next problem's `pre_have_` /
  `instr_…`. The in-flight `post_great_<theme>_<N>` finishes naturally
  — was previously cut mid-word.
- `useGameState.handleSubmit` (correct path) and `handlePuzzleSubmit`
  (correct path) bumped from **3000 ms → 5000 ms**. Gives the praise
  voice (~2.5–3s) time to finish + a settling beat before the new
  problem appears. Wrong-path retry stays at 3s.
